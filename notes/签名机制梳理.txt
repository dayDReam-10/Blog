# 签名机制梳理

最近有些人问我APK签名机制的原理，虽然早就了解过了，但讲给别人时发现他们不太明白，所以干脆写一篇笔记记录和梳理一下好了

在学习签名机制之前，我们需要先了解一下APK/ZIP的结构

## 布局

```text
[ entries 区 ][ Central Directory ][ EOCD ]
```

| 段 | 内容 |
|---|---|
| entries 区 | 每个文件的「头 + 压缩数据」，真正的内容 |
| Central Directory | 每个文件一条记录，含该文件在文件中的绝对偏移 |
| EOCD | 条目总数、目录大小、目录在文件中的绝对偏移 |

指向关系：

```text
EOCD ──(CD offset)─> Central Directory ──(local header offset)─> entries 
             指针                              索引
```

读取时：从尾部的 EOCD 出发，才能找到目录；从目录才能找到每个文件

### entries

#### 单个条目内部

```text
┌ 0x0000  条目 · a.dex ──────────────────────────────
│
│  0x04034b50  (4)  本地文件头标记

│  0x0000      (2)  标志位
│  0x0008      (2)  压缩方法 
│  0x0000      (2)  修改时间
│  0x0000      (2)  修改日期
│  crc_a       (4)  CRC-32，内容校验和
│  600         (4)  压缩后大小 
│  1000        (4)  解压后大小 
│  5           (2)  文件名长度
│  0           (2)  扩展字段长度
│  "a.dex"     (5)  文件名 
│
├ 头结束 0x0023 ──────────────────────────────────────
│
│  头长 = 30 固定 + 5 名字 + 0 扩展 = 35 字节

│  +-----------------------------------+
│  |  600 bytes                        |

│  +-----------------------------------+
│  ↑ 里面没有名字、没有长度、没有任何标记
│

```

## v1

### 三要素

| 文件 | 回答的问题 | 装的是什么 | 可读性 |
|---|---|---|---|
| `MANIFEST.MF` | 包里有 哪些文件 ，各自指纹多少？ | 文件名 + 文件内容的 SHA-256 | 纯文本 |
| `CERT.SF` | 这张清单 有没有被动过 ？ | 清单里每段文字的 SHA-256 | 纯文本 |
| `CERT.RSA` | 这个结论 是谁下的 ，凭什么信？ | 用私钥对 `CERT.SF` 的签名 + 证书 | 二进制 |

### 举例

```text
D_a = SHA-256( a.dex 这个文件的全部字节 )
D_b = SHA-256( b.dex 这个文件的全部字节 )

S_a = SHA-256( MANIFEST.MF 里 "a.dex 那一节的文字" )
S_b = SHA-256( MANIFEST.MF 里 "b.dex 那一节的文字" )

M   = SHA-256( 整份 MANIFEST.MF 的全部字节 )
MA  = SHA-256( MANIFEST.MF 的主属性段 )

t   = SHA-256( 整份 CERT.SF 的全部字节 )
```

### 第一层：MANIFEST.MF

`META-INF/MANIFEST.MF` 的实际字节：

```text
Manifest-Version: 1.0
Created-By: 1.0 (Android)

Name: a.dex
SHA-256-Digest: D_a

Name: b.dex
SHA-256-Digest: D_b
```

### 第二层：CERT.SF

`META-INF/CERT.SF` 的实际字节：

```text
Signature-Version: 1.0
Created-By: 1.0 (Android)
SHA-256-Digest-Manifest: M
SHA-256-Digest-Manifest-Main-Attributes: MA

Name: a.dex
SHA-256-Digest: S_a

Name: b.dex
SHA-256-Digest: S_b
```

```
`S_a` 指的是：

```text
S_a = SHA-256( "Name: a.dex
SHA-256-Digest: D_a" 这串字节)
```

它哈希的是  `MANIFEST.MF` 里 a.dex 那一节的三行文字 

| 写在哪个文件 | 属性名 | 值 | 这个值算的是 |
|---|---|---|---|
| `MANIFEST.MF` | `SHA-256-Digest` | `D_a` |  a.dex 文件的内容  |
| `CERT.SF` | `SHA-256-Digest` | `S_a` |  MANIFEST.MF 中 a.dex 那一节的文字  |

属性名一字不差，指代对象截然不同 `b.dex` 同理：`D_b` 管文件，`S_b` 管清单里的那几行字 

### 第三层：CERT.RSA

二进制，构造过程如下：

```text
t   = SHA-256( CERT.SF 的全部字节 )
sig = Sign_私钥( t )          ← RSA-2048 时 sig 为 256 字节

CERT.RSA = PKCS#7 SignedData {
    content      = CERT.SF 的字节,
    signature    = sig,
    certificates = [ 签名者证书链 ]
}
```
### 验证 a.dex 的实际顺序

```text
1. 从 CERT.RSA 取出证书链 → 拿公钥
2. 用公钥验 sig 对 CERT.SF 的签名
     通过 ⇒ CERT.SF 确实由持私钥者签发
3. 算 SHA-256(整份 MANIFEST.MF) 与 M 比对
     相等 ⇒ 清单未被修改
4. 算 SHA-256(a.dex 文件字节) 与 D_a 比对
     相等 ⇒ a.dex 未被修改
```

---

### 篡改实验

#### 场景一：只改 a.dex 一个字节

`D_a` 变为 `D_a'` ≠ `MANIFEST.MF` 中记录的 `D_a`

 结果：第 4 步失败，拒装或拒绝运行  

#### 场景二：改 a.dex，同时同步修改 MANIFEST.MF 里的 `D_a`

文件层通过了 但 `MANIFEST.MF` 里那节文字变了，导致重算的 `S_a'` ≠ `CERT.SF` 中的 `S_a`；同时整份清单变了，`M'` ≠ `M` 

 结果：两步都不匹配，失败  

#### 场景三：再连 CERT.SF 一起改，把 `S_a` 和 `M` 都更新

摘要全部自洽 但 `CERT.SF` 这个文件本身的字节变了，于是 `t` 变了，与 `CERT.RSA` 中 `sig` 对应的摘要不再一致 

 结果：公钥验签失败 链条断裂在需要私钥的那一步——而你没有私钥  

#### 场景四：一个字节都不改，只在 APK 文件最前面拼接一段数据

`a.dex`、`b.dex` 内容分毫未动，`D_a`、`D_b`、`S_a`、`S_b`、`M` 全部保持不变 

 结果：v1 校验完全通过  

但 DEX 解析器从文件第 0 字节读取 magic，它读到了拼接进去的那段数据 系统顺利执行了别人的代码，而所有摘要都显示"没问题" 

即  Janus（CVE-2017-13156） 

#### 场景五：往 entries 里新增 c.dex，什么都不改

`MANIFEST.MF` 里没有 `c.dex` 这一节 

JAR 规范 ：整份摘要 `M` 对不上没关系，退到逐节比对，`S_a`、`S_b` 仍然成立，判定验证 成功 ——它只承诺"签名时存在的文件未被修改" 

Android ：`c.dex` 不在清单里， 直接失败  

场景四，拼接：

```text
┌─────────────────────────────────────┐
│  恶意 DEX，从偏移 0 开始              │  
├─────────────────────────────────────┤
│  PK\x03\x04  a.dex 本地头            │
│  a.dex 数据                          │  
│  PK\x03\x04  b.dex 本地头            │
│  b.dex 数据                          │  
│  PK\x01\x02  目录记录 a.dex          │
│  PK\x01\x02  目录记录 b.dex          │
│  PK\x05\x06  EOCD                   │
└─────────────────────────────────────┘
```

场景五，新增条目：


```text
┌─────────────────────────────────────┐
│  PK\x03\x04  a.dex 本地头            │
│  a.dex 数据                          │  
│  PK\x03\x04  b.dex 本地头            │
│  b.dex 数据                          │  
│  PK\x03\x04  c.dex 本地头            │  ← entry 3，多出来的
│  c.dex 数据                          │
│  PK\x01\x02  目录记录 a.dex          │
│  PK\x01\x02  目录记录 b.dex          │
│  PK\x01\x02  目录记录 c.dex          │
│  PK\x05\x06  EOCD                   │
└─────────────────────────────────────┘
```
场景四多出来的是文件物理开头的一坨字节，不属于任何条目

场景五多出来的是一个完整的条目

v1 的校验动作是：遍历 MANIFEST.MF 里列出的每个文件，算它内容的 SHA-256，比对

```text
场景四：a.dex 内容没变，b.dex 内容没变  →  全对  →  通过

场景五：a.dex 内容没变，b.dex 内容没变  →  全对  →  通过

在 v1 眼里，这两个场景一模一样 它只看「条目内容」，两个场景都没动条目内容

而Android提出：MANIFEST.MF 里没列出的条目，视为非法

这条规则的作用对象是 条目列表——它遍历 ZIP 里所有条目，检查每一个能不能在清单里找到
```

## v2

### 签名前

```text
0x0000  ┌ 本地文件头 · a.dex            35
0x0023  │ a.dex 数据                    600
0x027B  ├ 本地文件头 · b.dex            35
0x029E  │ b.dex 数据                   1200
0x074E  ├ 目录记录 · a.dex              51   ┐
0x0781  ├ 目录记录 · b.dex              51   ┘ Central Directory
0x07B4  └ EOCD                           22
0x07CA    总计 1994 字节
```

### 签名原理

按 ZIP 的三个物理区域分别计算其哈希：

```text
段1  entries 区          
段2  Central Directory   
段3  EOCD                
```

三个哈希与证书共同构成 `signed data`，其字节序列再交由私钥签名：

```text
signed data
├ 三个哈希     
└ 证书                  

signature = Sign_私钥(SHA-256(signed data))
```

采用 RSA-2048 时签名值为 256 字节 签名仅能由持有私钥者生成，任何人都可用公钥验证 

因此修改文件内容后重新计算摘要并不构成有效绕过：`signed data` 的字节随之改变，而该字节序列已被私钥签名 

### 签名块构成与插入位置

```text
签名块
├ size                8     块长
├ ID-value 对区
│   ├ pair_len        8     对长度
│   ├ ID              4     类型标签，v2 为 0x7109871a
│   └ value                 该方案的载荷
│       ├ signed data       被签名对象
│       │   ├ 哈希组序列    每组含算法 ID 与三个哈希
│       │   ├ 证书序列
│       │   └ 附加属性序列
│       ├ 签名值序列        每项含算法 ID 与签名值
│       └ 公钥
├ size                8     块长，与首部数值相同
└ 魔数                16    "APK Sig Block 42"
```

然后插入于 entries 区之后、Central Directory 之前：

```text
0x0000  ┌ 本地文件头 · a.dex            
0x0023  │ a.dex 数据                    
0x027B  ├ 本地文件头 · b.dex            
0x029E  │ b.dex 数据                   
0x074E  ├ 签名块                     
0x0D4E  ├ 目录记录 · a.dex                   ┐
0x0D81  ├ 目录记录 · b.dex                   ┘ Central Directory
0x0DB4  └ EOCD                           
0x0DCA   
```

插入位置选为 Central Directory 起始偏移，这是因为这个位置使改动代价最低：

```text
entries 区         字节未变动
Central Directory  整体后移
                   其内部记录的条目偏移仍然有效
```

EOCD 中「Central Directory 偏移」字段的数值保持不变，该字段此时指向签名块起始位置，验证方据此定位签名块，再由块内记录的长度计算 Central Directory 的实际偏移

### 验证流程

验证自文件末尾向前推进：

```text
第 1 步   定位 EOCD
          从文件末尾向前搜索魔数 50 4B 05 06，命中 EOCD
          读出 EOCD 记录的「Central Directory 偏移」
          此处只是取数，不构成信任

第 2 步   用这个偏移去找签名块
          跳到该偏移处，即签名块起点
          读开头的块长字段
          按块长算出签名块末尾
          核对签名块末尾的魔数是否为 "APK Sig Block 42"
          不是 → 该位置没有签名块，终止

第 3 步   从签名块取出材料
          signed data（内含哈希1、哈希2、哈希3与证书）
          签名值序列
          公钥

第 4 步   验签名
          用公钥验证签名值对 signed data 的签名
          通过 → signed data 确由持私钥者签发 → 三个哈希可信
          不通过 → 终止

第 5 步   用哈希3校验段3
          对 EOCD 的全部字节算哈希，与哈希3比对
          通过 → 第 1 步读到的 EOCD 是原始的
               → 其记录的「Central Directory 偏移」也是原始的

第 6 步   此时 EOCD 可信，可照其定位
          Central Directory 实际起点 = 签名块起点 + 签名块总长

第 7 步   用哈希2校验段2
          对 Central Directory 的全部字节算哈希，与哈希2比对
          通过 → 索引未被修改
               → 其中记录的条目偏移可信

第 8 步   用哈希1校验段1
          对 entries 区的全部字节算哈希，与哈希1比对
          通过 → 两个条目内容均未被修改
```

### 篡改检测

```text
在文件起始处拼接数据      → 段1 字节变化  
在 entries 区新增条目     → 段1 长度变化 
修改 Central Directory    → 段2 字节变化  
修改 EOCD                 → 段3 字节变化  
```

在任何一处修改后重新计算摘要并替换，将导致 `signed data` 字节序列变化 该序列已被私钥签名，验证在第 2 步之后无法通过

## v3 

```text
v3 = v2 的签名机制 + 一条密钥轮换的授权记录
```

哈希计算、签名方式、签名块插入位置均与 v2 相同 v3 额外存储一份记录，说明当前签名密钥由哪把旧密钥批准 

```text
签名块  4928 字节
├ 0       8    size = 4904
├ 8    1504    对 1  ID = 0x7109871a
│                 ├ 8     pair_len = 1492
│                 ├ 4     ID
│                 └ 1492  v2 signer
├ 1512 3392    对 2  ID = 0xf05368c0
│                 ├ 8     pair_len = 3380
│                 ├ 4     ID
│                 └ 3380  v3 signer
├ 4904    8    size = 4904
└ 4912   16    "APK Sig Block 42"
```

### v3 signer 与 v2 signer 的结构差异

```text
v2 signer
├ signed data 长度 + signed data
├ 签名值序列长度 + 签名值序列
└ 公钥长度 + 公钥
```

```text
v3 signer
├ signed data 长度 + signed data
├ minSdkVersion                4     新增
├ maxSdkVersion                4     新增
├ 签名值序列长度 + 签名值序列
└ 公钥长度 + 公钥
```

`signed data` 内部同样增加了两项：

```text
v2 signed data                v3 signed data
├ 哈希组序列                   ├ 哈希组序列
├ 证书序列                     ├ 证书序列
└ 附加属性序列（空）            ├ minSdkVersion     4     新增
                              ├ maxSdkVersion     4     新增
                              └ 附加属性序列
                                  └ proof-of-rotation  新增
```

### proof-of-rotation 内部

以完成一次密钥更换（A → B）为例，一条记录：

```text
proof-of-rotation
├ 版本号                     4    值为 1
├ 记录长度                   4
└ 记录
    ├ 签名算法 ID            4
    ├ 已签名数据长度          4
    │   ├ 上一代证书长度      4
    │   ├ 上一代证书 A       796
    │   ├ 签名长度           4
    │   └ 签名值             256   对「新证书公钥」的签名
    └ 新证书长度             4
        └ 新证书 B           796
```

多处更换时追加记录，形成链：

```text
A 批准 B → B 批准 C → C 批准 D
```

## 机制

更换密钥时，由旧私钥出具一份授权记录：

```text
1. 取新证书 B 的公钥
2. 用旧私钥 A 对该公钥签名
3. 将「旧证书 A」与「该签名」组成一条记录
4. 将记录放入新版本 APK 的签名数据内
```

## 验证流程

```text
1. 以 B 的公钥验证 APK 的签名值
   通过 → APK 由 B 签发
2. 取出授权记录，其中声明新公钥为 B 的公钥
3. 以 A 的证书中的公钥验证记录中的签名
   通过 → 记录确由 A 出具
4. 核对记录声明的公钥与当前签名所用公钥一致
```

四步全部通过，系统判定身份连续，允许覆盖安装 

## 多次更换

```text
记录 1    A 批准 B
记录 2    B 批准 C
```

系统自当前密钥起逐条向前验证，直至回到最初的密钥

## 与 v1、v2 的关系

三者均为签名方案，差别在于能证明的内容范围：

```text
v1   保护每个条目的内容     证明内容未变、由哪把密钥签发
v2   保护整个文件的三段字节  证明全部字节未变、由哪把密钥签发
v3   保护范围同 v2          额外证明当前密钥是原始密钥的合法继任者
```

三套签名可同时存在于同一 APK 中，系统按自身支持的版本择高使用：

```text
Android 6.x 及以下    走 v1
Android 7.x           走 v2
Android 9 及以上       走 v3
```
